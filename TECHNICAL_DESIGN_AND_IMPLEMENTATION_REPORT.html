1. Executive Summary

Modern enterprise systems depend on decoupled, asynchronous processing pipelines to handle long-running computations, external integrations, recurring maintenance, and batch jobs without blocking user-facing request threads. The Distributed Job Scheduler is a production-inspired, fault-tolerant background execution platform engineered as a modular monolith in Java 21 and Spring Boot 3.3.4, backed by an ACID-compliant PostgreSQL database, secured via Keycloak OpenID Connect (OIDC) JWT tokens, and administered through a Next.js 14 real-time dashboard.

  • Zero Duplicate Execution: Eliminates worker race conditions under high concurrency using native PostgreSQL FOR UPDATE SKIP LOCKED row-level locking.
  • Queue Concurrency & Dispatch Control: Enforces dynamic per-queue concurrency limits and safe queue pause/resume controls without interrupting active worker processes.
  • Configurable Resilience & DLQ: Supports Fixed, Linear, and Exponential backoff retry policies, routing exhausted failures to a Dead Letter Queue (DLQ) with stack trace capture and 1-click re-queueing.
  • Worker Liveness & Failover: Tracks 5-second worker heartbeats and automatically reclaims orphaned jobs from crashed nodes via a 60-second stale worker detection loop.
  • Full Observability: Records attempt-level durations, worker node assignments, structured step-by-step logs, and JSON result data.

7. Reliability and Concurrency

Duplicate task execution is prevented at the database layer using an atomic Common Table Expression (CTE) with row-level locks: 

WITH eligible_jobs AS (
    SELECT j.id
    FROM jobs j
    JOIN queues q ON j.queue_id = q.id
    WHERE j.status = 'QUEUED'
      AND j.scheduled_at <= CURRENT_TIMESTAMP
      AND q.is_paused = FALSE
      AND (
          SELECT COUNT(*)
          FROM jobs r
          WHERE r.queue_id = q.id AND r.status = 'RUNNING'
      ) < q.concurrency_limit
    ORDER BY j.priority DESC, j.scheduled_at ASC, j.created_at ASC
    FOR UPDATE OF j SKIP LOCKED
    LIMIT :batchSize
)
UPDATE jobs
SET status = 'CLAIMED',
    locked_by_worker_id = :workerId,
    locked_at = CURRENT_TIMESTAMP,
    updated_at = CURRENT_TIMESTAMP
WHERE id IN (SELECT id FROM eligible_jobs)
RETURNING *
  • FOR UPDATE OF j SKIP LOCKED: Instructs PostgreSQL to lock candidate rows. If another worker thread holds a lock, that row is skipped instantly without blocking.
  • Queue Concurrency Enforcement: Evaluates active RUNNING jobs in the queue against concurrency_limit during the claim transaction.
  • Worker Heartbeats & Recovery: Active workers update heartbeats every 5 seconds. Stale workers silent for $> 60$ seconds are marked DEAD, and their orphaned jobs are safely recovered.

11. Key Design Decisions and Trade-offs

Decision Reason Benefits Trade-offs / Limitations
PostgreSQL SKIP LOCKED Avoids external broker complexity while guaranteeing transactional consistency. Strict ACID guarantees; zero broker sync lag; job state and data commit together. Database polling load scales with high worker counts; requires index maintenance.
Spring Boot 3.3 & Java 21 Enterprise-grade asynchronous runtime and type-safe ecosystem. Declarative transactions (@Transactional), rich testing, and virtual thread readiness. Higher memory footprint than compiled Go/Rust binaries.
Keycloak OIDC Security Standards-compliant authentication decoupling identity from business logic. Centralized user directory, role mapping (ADMIN, DEVELOPER, OPERATOR), PKCE flow. Requires Keycloak instance for token issuance.
Decoupled Execution Tables Isolates active job state from attempt history and step logs. Keeps primary queue table lean and performant; provides complete audit trail. Requires log pruning policies for long-term database maintenance.
